# v2.0.1：捕获后移（倒计时结束才取流）——倒计时期弹窗稳定

## 调研结论

- 平台机制确认：捕获流程会拿走激活焦点，Chrome 按设计在弹窗失焦时关闭它；无公开的 156 回归条目，但你的 Chrome 156.0.8078.48 为本月自动升级的新版本，"昨天之前没问题"与自动升级时间线吻合（版本号本身即证据，与代码版本无关）
- **功能级解法（不依赖根因定性）**：把捕获动作从"点开始瞬间"推迟到"倒计时归零"。点开始后只做预约（ensureOffscreen + 计划），倒计时期什么都不发生 → 弹窗稳定显示全程倒计时，你在页面上点播放；归零时才签发 streamId + getUserMedia + 开始录制——此时你已在播放页，弹窗关闭无碍

## 改造（v2.0.1）

### 启动流重构（两点式 → 预约式）
1. **popup 点开始** → SW：仅 `ensureOffscreen` + 注入检测器也一并后移（点开始瞬间只剩"开 offscreen + 发预约"两个动作，最小化秒关面）
2. **offscreen 新增 `offscreen-schedule`**：存 settings/payload → `state=countdown` → 徽章倒计时（照常）→ 归零时发 `{type:"request-capture"}`
3. **SW `request-capture`**：`getMediaStreamId`（activeTab 仍在）+ `injectDetector` → 返回 streamId → offscreen `getUserMedia` + 回环 + 开录
4. **失败路径**：倒计期间导航导致 activeTab 失效 → request-capture 失败 → 状态窗/面板显示「启动失败：请在播放页重新点开始」；倒计期间停止 → 干净取消（无文件）
5. 复验时的**诊断价值**：若弹窗现在能稳定撑过整个倒计时、恰在归零时关闭 → 实锤捕获指示焦点行为；若点开始仍秒关（此时点开始已几乎无动作）→ 另有元凶，继续二分
